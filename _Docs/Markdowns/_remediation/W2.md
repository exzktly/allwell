data, so each fix here is judged against the same rule: degraded output must
never be indistinguishable from good output.

regression test below was watched failing against a worktree of `cc18d88c` —

## Item 18 — the "did anything land?" check skipped the empty archive — done

**Fix:** `datasets/subset/apply.py:283-300` (the `kept_in_names` sentinel and
the row check that reads it).

`kept_in_names` was a `frozenset` initialised to empty, and the row check read
`if fname and kept_in_names and fname not in kept_in_names`. That truthiness
test conflated "there was no raw-input container to compare a row against"
with "there was one and the filter kept nothing from it" — so the one archive
that certainly cannot hold a row's image was the one archive whose rows went
unchecked. It is now `frozenset | None`: `None` for no container, an empty set
for a container that kept nothing, and the check runs for both real cases.

**Test:** `tests/test_subset_verification_gaps.py::test_a_row_is_checked_even_when_the_filter_emptied_the_well_s_archive`,
plus two controls that must keep passing —
`::test_a_well_whose_archive_kept_members_is_still_checked` and
`::test_a_well_with_no_raw_input_container_at_all_is_still_copied`.

**Watched fail:** yes — `Failed: DID NOT RAISE SubsetError` against `cc18d88c`.

**Probe:** a source whose `in/A01.zip` had lost its 24h image, filtered to 24h.
Before: `Subset written to …/dest (2 well(s))`, `dest/in/` holding only
`B02.zip`, and `dest/out/measurements_A01.csv` carrying a row naming
`exp_GFP_A01_F001_24h.tif` — a file nowhere in the destination. After: the run
raises, naming the file *and* saying the filter kept no member of that archive
at all, so the reason there is nothing to point into is explicit rather than
implied.

## Item 67 — a member that failed the rewrite gate kept dataset 2's well — done

**Fix:** `datasets/merge_plates/apply.py:83` (`_carries_a_well_token`),
`:125` (`_remap` now records the flag it used to discard), `:167`
(`_refuse_unrewritten`), and its three call sites at `:229`, `:253`, `:315`.

`_remap._rename` called `rewrite_member_field(...)[0]` and threw away
`was_rewritten`. A member failing the structural gate — one separator-delimited
field too many, an extension the role catalog does not know, a well token that
is not the source well — therefore landed in the *destination* well's archive
still spelled with dataset 2's well, and the merge reported success. The CSV row
went unrewritten identically, so the `dest_in_names` cross-check compared two
consistent wrong answers and passed.

The entitlement half matters as much as the refusal: `.DS_Store`, an AppleDouble
`._` sidecar and a `readme.txt` a user put in on purpose all fail the same gate,
carry no well token, and must pass through untouched. `_carries_a_well_token`
decides which members the question may be asked of at all — not OS junk
(`is_os_junk_member`) and a catalogued image extension (`IMAGE_EXTS`).

The CSV branch (`:315`) is checked separately from the archive branches on
purpose: a well with no `in/<WELL>.zip` at all has no members to walk, and that
is the one case the archive-side refusal cannot cover.

**Test:** `tests/test_merge_plates_unrewritten_members.py::test_an_image_whose_well_token_will_not_move_refuses_the_merge`
(parametrised over both failing shapes),
`::test_the_csv_alone_refuses_it_too_when_the_well_has_no_raw_input`, and the
entitlement control `::test_os_debris_and_a_stray_text_file_still_pass_through_a_remap`.

**Watched fail:** yes — 3 failed / 1 passed against `cc18d88c`, all three with
`Failed: DID NOT RAISE MergePlatesError`. The control passed on both sides,
which is what it is for.

**Probe:** ds2's `A01.zip` given an extra member
`exp_GFP_A01_F001_24h_rescan.tif` plus a matching CSV row, remapped A01 → B02.
Before: `Merged 2 well(s)`, with `dest/in/B02.zip` holding
`exp_GFP_A01_F001_24h_rescan.tif` beside two correctly-renamed B02 images, and
a CSV row reading `well=B02, filename=exp_GFP_A01_F001_24h_rescan.tif`. After:
the merge refuses and names the file, the two wells, and why.

## Item 68 — in-place mode's scope was wider than its preview — done

**Fix:** `datasets/import_loose/import_loose_compute.py:194`
(`existing_well_folders`), `:110` (`ImportPreview.existing_folder_note`), `:72`
(the new field), `:277` (`scan_folder` populates it);
`datasets/import_loose/apply.py:319-347` (the run's own log line and summary);
`datasets/import_loose/view.py:378` (readout), `:453`
(`existing_folder_note` accessor), `:98` (the readout refresh — see below);
`datasets/import_loose/controller.py:181` (the confirmation dialog).

The in-place conversion zips and unlinks the TIFs of **every** well-named
subfolder under the source, including pre-existing ones. That scope is
deliberate — it is what leaves the folder in one uniform ready-to-run layout,
and what lets an interrupted run resume, since a crashed attempt's already
grouped wells have no loose TIFs left to find — so it was **announced, not
narrowed**. Narrowing it to the wells `run_zipper` reported would have broken
the resume path in exactly the `--move-source-tifs` case where it matters.

`existing_well_folders` walks the same shape `_zip_well_folders` walks (top
level only, a directory whose name canonicalises to a well, at least one
`.tif`/`.tiff` directly inside), so the number the page shows is the number the
run acts on rather than a second nearby estimate.

**A second defect found while testing this.** `_on_in_place_toggled` never
refreshed the readout, so the new sentence was unreachable through the control
that decides whether it applies — the §7.6 shape exactly. A test that called
`refresh_readout()` directly would have passed; the one that ticks the real
checkbox failed. Fixed at `datasets/import_loose/view.py:98`.

**Test:** `tests/test_import_loose_scope.py::test_the_run_summary_names_the_extra_scope`
(the behavioural proof),
`::test_the_announced_folders_are_exactly_the_ones_the_run_converts`,
`::test_the_preview_names_the_well_folders_an_in_place_run_will_also_zip`,
`::test_a_folder_with_no_pre_existing_well_folders_says_nothing`,
`::test_the_page_states_the_extra_scope_once_the_destructive_mode_is_armed`.

**Watched fail:** yes, 5 of 5 against `cc18d88c` — but read the failure types.
Only `::test_the_run_summary_names_the_extra_scope` fails with a real
`AssertionError` (`'C03' in 'Grouped loose TIFs in … into 4 per-well zip(s).'`
— the base run converted four wells while its preview said two, and said
nothing). The other four fail with `AttributeError` on `existing_well_folders`
/ `existing_folder_note`, which is inherent: the base measures this scope
nowhere, so there is no old value to assert against. They are regression guards
on a new API, not proofs of the fix. The summary test is the proof.

**Probe:** a folder with two loose TIFs (A01, B02) and two pre-existing well
folders (C03, D04, one carrying an `acquisition.log`). Before: preview said
"2 well(s)"; apply zipped C03 and D04, deleted their TIFs, removed D04/
entirely, and the summary said only "4 per-well zip(s)". After: the preview,
the readout (once in-place is armed), the confirmation dialog, the run log and
the summary all name C03 and D04, and the run behaves identically.

## Item 69 — `row_matches` and `member_matches` read different sources — done

**Fix:** `datasets/subset/subset_compute.py:250` (`row_hours`), `:289`
(`row_verdict`), `:313` (`row_matches` is now a thin wrapper);
`datasets/subset/apply.py:130` (`_verify` names the cause it can see) and
`:285-290` (apply reads `row_verdict` and counts the unjudgeable rows).

`row_matches` read `float(row["timepoint_hours"])` and returned `False` on a
blank; `member_matches` parsed the filename's timepoint token. A legacy CSV that
leaves the numeric column blank therefore failed every row against a filter
every image passed — the images copied, the measurements did not — and
`_verify` then blamed the filter.

### Sweep — timepoint predicate sites

Converted (all now resolve a row's timepoint through `row_hours`, which tries
the numeric column, then the `timepoint` label column via `parse_hours`, then
the `filename` column's own token — literally the value `member_matches` reads,
so the last fallback makes the two predicates read the identical token):

* `datasets/subset/subset_compute.py::row_matches` — the reported site.
* `datasets/subset/subset_compute.py::row_verdict` — new; the same predicate
  with the third state (`ROW_UNJUDGEABLE`) the old boolean collapsed away.
* `datasets/subset/apply.py::_copy_one_well` — the only caller in the copy
  path; now passes `plan.schema` / `plan.channels` so the filename fallback is
  reachable. A `row_matches` call without them silently loses that fallback,
  which is why both new parameters are keyword-only and default to `None`/`()`.

Deliberately **left**, with the reason:

* **The FOV axis of `row_matches`.** `normalize_fov("")` returns `"1"`
  app-wide (`well_viewer/data/image_identity.py`, and `CellKey.from_row` in the
  override reader). On a single-FOV dataset a blank FOV column *is* FOV 1, not a
  missing value. Reading it as undefined here would have invented a second
  meaning for a blank that the rest of the app has already settled — the
  opposite of the sweep's purpose. Documented in `row_verdict`'s docstring.
* **`datasets/concatenate/concatenate_compute.py`'s timepoint handling.** It
  *rewrites* a timepoint rather than filtering on one, and it already reads the
  label column and the filename in lock-step (ARCHITECTURE §6b's four coupled
  values). It answers "what should this become", not "does this match", so it
  is not a sibling of this predicate.
* **`datasets/validate/validate_compute.py`'s timepoint scans.** They report
  drift rather than deciding what to copy; a fallback there would mask exactly
  the disagreement Validate exists to surface.

`_verify` now distinguishes three causes instead of printing one message for
all of them: rows that could not be tested at all, zero rows beside images that
matched the same filter, and a genuinely empty match.

**Test:** `tests/test_subset_verification_gaps.py::test_a_legacy_csv_with_no_timepoint_hours_column_still_subsets`,
`::test_the_filename_column_is_the_last_resort_for_a_row_s_timepoint`,
`::test_rows_that_state_no_timepoint_at_all_are_named_as_the_cause`,
`::test_zero_rows_beside_matching_images_does_not_blame_the_filter`.

**Watched fail:** yes — all four with real `AssertionError`s against
`cc18d88c`, including `row_matches({... 'timepoint_hours': ''}) == False` and
the old blanket "check that the filter actually matches data" message.

**Probe:** a dataset whose CSVs had `timepoint_hours` blanked, filtered to
24h+48h. Before: `SubsetError: … wrote zero measurement rows … check that the
filter actually matches data`, while `dest/in/A01.zip` had happily received
four images. After: the subset completes, the CSV keeps the four matching rows,
and the images and rows agree.

## Item 70 — `A1.zip` and `A01.zip` collapsed by dict overwrite — done

**Fix:** `datasets/_common/dataset_paths.py:187` (`in_containers`, now
deterministic and documented), `:230` (`well_spelling_collisions`), `:292`
(`describe_well_collisions`); refused in each copy tool's plan builder at
`datasets/subset/subset_compute.py:125` (called at `:168`),
`datasets/merge_plates/merge_plates_compute.py:72` (called at `:352-353`) and
`datasets/concatenate/concatenate_compute.py:246` (called at `:467-468`) —
each a `_refuse_well_collisions` calling the shared detector with its own error
class.

The four maps can each hold one path per canonical well, so they *cannot*
represent "two files claim this well" — which is why the fix is not inside them.
Two things changed: the survivor is now deterministic (sorted glob, and the
spelling that already equals the canonical label wins) rather than
filesystem-order dependent, and the folder is asked directly, once, before any
copy tool writes anything.

### Sweep — "how many files claim this well?" sites

Detected and refused:

* `in/<WELL>.zip` — two zips for one well. **The reported site.**
* `in/<WELL>/` — two raw-input folders for one well.
* `out/<WELL>_out.zip` — two QC archives for one well.
* `out/<WELL>/` — two folder-mode QC folders for one well.
* `out/<prefix>_<WELL>.csv` — two measurements CSVs for one well **under the
  same `--csv_prefix`**, keyed on `(prefix, well)`.

Deliberately **left**, with the reason:

* **A zip beside a same-well folder** (`in/A01.zip` + `in/A01/`). Not a
  collision: `process_microscopy` ignores well folders whenever any zip is
  present, so the two layouts have a settled precedence and `in_containers`
  follows it. Refusing here would reject a layout the pipeline reads correctly.
* **Two CSVs for one well under *different* prefixes**
  (`measurements_A01.csv` + `nuclei_A01.csv`). This is the mixed-prefix state
  `out_csvs`' docstring already documents and Validate already reports with a
  cause of its own. It is a different question from one plate position being
  spelled two ways; refusing it here would make every copy tool reject a dataset
  Validate merely comments on. Pinned by
  `::test_two_csv_prefixes_for_one_well_are_not_a_spelling_collision`.
* **`out_csvs`' own overwrite comment.** Left as-is; it names the caller
  (Validate) that must not trust the map, and that contract is unchanged.
* **Validate itself does not yet report spelling collisions.** See
  *Cross-package dependencies* below — it is the natural home for a `Finding`,
  and it is not in this package's file list.

**Test:** `tests/test_well_spelling_collisions.py::test_subset_refuses_a_dataset_that_spells_one_well_two_ways`,
`::test_merge_plates_refuses_it_on_either_side`,
`::test_concatenate_refuses_it_too`,
`::test_a_measurements_csv_duplicated_under_one_prefix_is_refused`,
plus the two controls
`::test_two_csv_prefixes_for_one_well_are_not_a_spelling_collision` and
`::test_a_healthy_dataset_with_real_archive_debris_is_not_refused`.

**Watched fail:** yes — 4 failed / 3 passed against `cc18d88c`, all four with
`Failed: DID NOT RAISE`. One caveat, stated plainly:
`::test_the_surviving_container_is_deterministic_not_glob_order` **passed** on
the base, because that tmp dir's glob happened to return `A01.zip` first. It is
a regression guard on a property that used to hold only by accident, not a
proof — and it cannot be made to bite reliably, since the thing it pins is
precisely that the answer no longer depends on the filesystem.

**Probe:** a dataset with `in/A01.zip` + `in/A1.zip` and
`out/A01_out.zip` + `out/A1_out.zip`, subset to well A01. Before:
`in_containers` returned `{'A01': A01.zip, 'B02': …}`, the run reported
`Subset written to …/dest (1 well(s))`, and `A1.zip`'s two images existed
nowhere in the destination and were mentioned in no count. After: the plan
builder refuses before anything is written, listing all four files by name.

## Item 73 — `resolve()` conflated a symlink with its target — done

**Fix:** `util/zip_write.py:114` (`_entry_identity`), `:139` (`_is_under`),
`:193-207` (the archived set and the walk in
`replace_folder_with_archive`).

Identity was `Path.resolve()` on both sides, which follows the final component,
so a symlink and the file it points at came back as one path. Both directions
lost something. Identity is now `(os.path.realpath(path.parent), path.name)`:
a symlinked ancestor directory still cannot split two spellings of one folder
apart, while the final component stays lexical — the level a zip member name
lives at, and the level at which two hard links to one inode are correctly two
entries. The walk now counts every entry that is not a real directory, symlinks
(including dangling ones and links to directories) included.

**Test:** `tests/test_zip_write_symlink_aliases.py::test_a_link_the_archive_has_no_member_for_survives_the_folder_removal`,
`::test_an_archived_link_out_of_the_folder_is_not_reported_as_kept`,
`::test_a_broken_link_left_behind_keeps_the_folder`,
`::test_a_second_hard_link_to_an_archived_file_is_a_second_entry`,
`::test_the_ordinary_case_is_unchanged`,
`::test_a_path_outside_the_folder_is_still_ignored`.

**Watched fail:** yes — 3 failed / 3 passed against `cc18d88c`, with real
`AssertionError`s (`assert () == ('alias.tif',)` and
`assert ('linked.tif', 'notes.txt') == ('notes.txt',)`). The hardlink test, the
ordinary case and the outside-path safety test passed on both sides: the
hardlink shape was already correct (the brief's second direction is realised by
a *symlink*, not a hard link), so that one is a regression guard rather than a
proof, and the other two are controls.

**Probe:** (A) a folder with `real.tif` and a symlink `alias.tif` → `real.tif`,
only `real.tif` archived. Before: `kept=()`, `folder_removed=True` — the whole
folder removed, taking a name the archive holds no member for. After:
`kept=('alias.tif',)`, folder and link survive, `real.tif` removed.
(B) a folder with `notes.txt` and an archived `linked.tif` pointing outside.
Before: `kept=('linked.tif','notes.txt')` — a caller's "not archived" log line
naming a file that was archived — and the link never removed. After:
`kept=('notes.txt',)`, the link removed, its target untouched.

## Item 74 — same-basename files silently overwrote each other — done

**Fix:** `WellPlateZipper.py:171` (`_same_file`), `:210-241` (`folder_well`:
first-write-wins, a per-collision stderr warning, and a survivor count).

`copy2`/`move` onto an existing name simply overwrite. Under `--recursive` two
subfolders can hold one basename; with `--move-source-tifs` the loser's original
was removed as well, so one image existed nowhere afterwards. The progress line
the Analyze tab parses printed `len(files)` — the source count.

Now first-write-wins (the rule the zip writers already apply to a duplicate
member name), the loser is left where it is, the collision is named on stderr
with both paths (`run_zipper` merges stderr into the Analyze log), and the
count is what actually landed. `_same_file` additionally makes a file already
sitting in its own well folder a no-op instead of a `shutil.SameFileError`
crash — the state a recursive re-run over `--output-dir == --search-dir`
produces.

Note the app never passes `-r`: `services/input_resolution_service.build_zipper_cmd`
has no `--recursive`, so this is a CLI-only data-loss path. It is still a
documented, supported entry point.

**Test:** `tests/test_zipper_basename_collisions.py::test_a_colliding_copy_is_skipped_and_counted_honestly`,
`::test_move_mode_leaves_the_loser_s_original_on_disk`,
`::test_a_file_already_in_its_own_well_folder_is_not_a_collision`,
`::test_the_ordinary_non_colliding_case_is_unchanged`.

**Watched fail:** yes — 3 failed / 1 passed against `cc18d88c`. Two are real
`AssertionError`s, and the second is the data-loss proof outright:
`assert {b'first', b'other', b'second'} <= {b'first', b'other'}` — `b'second'`
existed nowhere on disk after the move. The third
(`::test_a_file_already_in_its_own_well_folder_is_not_a_collision`) fails at
base with `shutil.SameFileError` rather than an assertion; that is a crash the
fix also removes, not a false proof, but it is an exception and not an
assertion, so it is named here as such.

**Probe:** two subfolders each holding `exp_GFP_A01_F001_24h.tif`, grouped
recursively. Before: `A01: 3 files` printed, 2 files on disk, nothing on stderr,
and under `--move-source-tifs` one image's bytes gone entirely. After:
`A01: 2 files`, a stderr line naming the file that was not grouped and where it
was left, and every byte that existed before the call still on disk after it.

## Item 76 — the `seg_fp` restamp was assigned inside `with swallow(...)` — done

**Fix:** `datasets/_common/containers.py:439` (`restamp_overrides`), `:482`
(`unstamped_note`); the three sites now call it —
`datasets/subset/apply.py:122`, `datasets/merge_plates/apply.py:349`,
`datasets/concatenate/apply.py:437`.

`entry["seg_fp"] = f"{zip_path.stat().st_mtime_ns}"` sat *inside* the
suppression, so a failed stat left the **source** dataset's fingerprint on the
carried-over entry. (`swallow` is the context manager and was used correctly —
the bug is the assignment target being under it, not the `swallow`/`swallowed`
mix-up.) Validate then compared that against the destination archive, found it
different, and pruned the entry: the user's manual cell exclusions vanished with
every step reporting success.

A fingerprint that could not be computed is not a fingerprint, so the key is
now removed. An entry with no `seg_fp` is the legacy unfingerprinted shape both
readers already understand and keep
(`well_viewer/persistence/cell_overrides.py:156`,
`datasets/validate/apply.py:83`). The count of unstamped entries is returned
rather than logged inside the helper, so each tool states it in its own
cell-override log line — the shortfall is in the artifact's own summary, not
only implied.

All three sites were identical, so they were converged onto one helper rather
than patched three times; that is what makes them unable to drift apart again.

**Test:** `tests/test_override_restamp.py::test_subset_drops_a_fingerprint_it_could_not_compute`,
`::test_merge_plates_does_the_same`, `::test_concatenate_does_the_same`,
`::test_validate_keeps_the_carried_override_instead_of_pruning_it`, and the
control `::test_a_fingerprint_that_can_be_computed_is_still_stamped`.

**Watched fail:** yes — 4 failed / 1 passed against `cc18d88c`, all four with
real `AssertionError`s, including the end-of-chain one
(`assert _prune_stale_overrides(...) == 0` returning `1`).

**Probe:** a source with a well that has measurements but no `<WELL>_out.zip`,
carrying one override stamped `111111111111`. Before: the destination's
`cell_overrides.json` held `seg_fp: '111111111111'` — the source's — and a
subsequent Validate run pruned it, leaving zero overrides. After: the key is
absent, the log line says how many could not be fingerprinted and what that
means, and Validate prunes nothing.

## Cross-package dependencies

Each of these needs a file outside this package's ownership, so none was made.

1. **`_Docs/Markdowns/ARCHITECTURE.md` is not updated.** This package adds a
   contract (`well_spelling_collisions` — every Datasets copy tool refuses a
   dataset that spells one well two ways), changes another (a carried-over cell
   override with no computable fingerprint is carried *without* one rather than
   with the source's), changes the well-token rewrite from best-effort to
   refuse-on-failure in Merge Plates, and changes what
   `replace_folder_with_archive` treats as one file. ARCHITECTURE is shared with
   three other workers, so it was left for the lead.
2. **`_Docs/Markdowns/README_WellViewer.md` is not updated.** Two user-visible
   changes: Import Loose's page and confirmation now name the pre-existing well
   folders an in-place run will also zip and empty, and the Datasets copy tools
   now refuse a dataset holding two spellings of one well.
3. **Validate does not report a well-spelling collision.**
   `datasets/validate/validate_compute.py` is the natural home for a `Finding`
   built from `well_spelling_collisions` — Validate's whole job is to name this
   class of dataset problem, and a user who hits the copy tools' refusal has
   nowhere to go and check the rest of the plate. Not done here: it is a large
   shared file and outside the item's scope. Recommended follow-up.
4. **`services/input_resolution_service.build_zipper_cmd` never passes `-r`.**
   Item 74's collision is therefore CLI-only today. If the GUI ever gains a
   recursive option, the warning path this fix adds becomes user-visible and
