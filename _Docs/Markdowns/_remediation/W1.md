Nine items. Every one is `done`: the fix is in the tree, a regression test pins
it, and the test has been watched failing against pre-fix code.

**How the proofs were run.** `scripts/prove_guard.sh <test> <ref>` builds a
worktree of *ref*, copies the test into it and requires a real
`AssertionError`. The first four items were proved against `HEAD` while HEAD was
`598ebb01`; partway through this work the branch lead committed the in-flight
tree as `deb4dcd4`, which put these fixes *on* HEAD, so every later proof names
`598ebb01` explicitly. Where a test file also contains a case that exercises a
symbol the fix introduces, that case was excluded from the proof run with `-k`,
because a red run caused by an `ImportError`/`AttributeError` measures nothing
(CLAUDE.md §7.4 #4).

(`…/scratchpad/probes/p80.py` … `p88.py`), not in the repository.

## Item 80 — v2 staleness fingerprint fails open — `done`

**Fix:** `well_viewer/persistence/cell_overrides.py`

* lines 63–70 and 113–116 — `except OSError: pass` in both fingerprint
  snapshots is now `swallowed("cell_overrides: could not stat …")`.
* lines 164–182 — a stored fingerprint with **no** current fingerprint to
  compare against (the well's `<well>_out.zip` is not in the data directory) is
  counted as `unverifiable` instead of falling through the
  `if current_fp and stored_fp != current_fp` test. The row is still loaded —
  dropping curation because a zip moved would be an unrecoverable loss — and a
  warning names how many were kept unchecked.
* lines 195–213 — the "no fingerprint" warning no longer requires
  `file_version < 2`. A v2 file can hold rows with an empty `seg_fp` (the zip
  was missing or unreadable at save time), and gating the warning on the file
  version meant exactly that file warned about nothing. The version is now
  reported inside the message instead of deciding whether to emit it.

**Test:** `tests/test_cell_overrides_unverified_fingerprints.py::test_v2_row_without_a_fingerprint_warns`,
`::test_stored_fingerprint_with_no_zip_on_disk_is_reported`,
`::test_verified_row_produces_no_unchecked_warning`.
Watched failing on `HEAD` (= `598ebb01`): *"a v2 file carrying a row with an
empty seg_fp warned about nothing; records were []"* and *"the row whose well
has no _out.zip passed the staleness guard silently"*.

**Probe:** a v2 file with three rows — one stale (zip re-run), one whose well
has no zip, one with an empty `seg_fp`. Before: one warning, about the stale row
only; the other two loaded in silence. After: three warnings, and the same three
rows load.

## Item 85 — unlocked read-modify-write of `pipeline_info.json` — `done`

**Judgement:** no lock. A lock would need every writer of that file, in every
process, to honour it — and the pipeline runs in a separate process, often on a
remote host. What is implemented instead is optimistic concurrency in one shared
helper: `well_viewer/persistence/_io.update_json_atomic(path, mutate, …)` reads
the file's bytes, calls `mutate`, re-reads and compares **byte for byte**
immediately before the replace, and re-applies the mutation to the new content
when another writer has landed in between. Content, not mtime — two writes
inside one filesystem timestamp tick are exactly the case this must catch. That
narrows the window from "however long the caller takes to build its block" to
the microseconds between the comparison and `os.replace`. The residual race is
deliberate and is documented in the helper's docstring.

**Fix:**

* `well_viewer/persistence/_io.py:148–…` — the new helper.
* `well_viewer/persistence/smfish.py:78–87` (`clear_thresholds`) and
  `:129–157` (`save_threshold`) route through it.
* `well_viewer/domain/gating_state.py:221–240`
  (`save_gating_to_pipeline_info`) routes through it.

**Test:** `tests/test_pipeline_info_concurrent_update.py` — three cases
(threshold save, gating save, threshold clear), each with the pipeline's own
rewrite injected at the file itself, immediately after the viewer's first read.
Watched failing on `598ebb01`: *"the run's fluor_tokens were reverted by the
threshold write: ['gfp']"* and the same for the gating write.
`tests/test_update_json_atomic.py` covers the helper's own contract (refusals,
the re-apply, and giving up loudly after the attempt budget); it is new API, so
it cannot be proved red on the base and is not offered as proof.

**Probe:** a sidecar the pipeline rewrites with `fluor_tokens: [gfp, cy5]` and
four timepoints while the viewer is saving an smFISH threshold. Before: the file
ends up with `['gfp']` and two timepoints — the run's keys reverted. After: both
the run's keys and the threshold are present.

**Cross-package dependency:** `well_viewer/domain/sample_definitions.py::save_to_pipeline_info`
performs the same unlocked read-modify-write of `pipeline_info.json` (read,
merge `sample_definitions`, `write_json_atomic`). That file is not in this
package's ownership list. It should be routed through
`well_viewer.persistence._io.update_json_atomic` in the same shape as the two
sites above — note it must keep its pre-v2 backup step, which has to run inside
the mutate callback or before the loop.

## Item 86 — no-data early return keeps the previous dataset's range — `done`

**Fix:** `well_viewer/core/channel_state_controller.py`

* new `reset_threshold_range(channel_state)` (just above `_recalculate_threshold`)
  puts the range back to `ChannelState`'s **declared** defaults, read off a
  fresh instance rather than written as literals so the two cannot drift.
* inside `_recalculate_threshold`, the `if all_vals.size == 0` branch calls it
  and logs before returning. Undefined is not unchanged: `begin_load` clears the
  per-column cache and nothing else, so returning left `threshold_min` /
  `threshold_max` holding the closed plate's numbers.

The `return` itself is kept. The gating-hydration tail below it is documented
(in the comment above the feature-hook fan-out) as deliberately running only
after the no-data early return, and `load_controller` calls
`_load_gating_from_pipeline_info` separately in the same load.

**Test:** `tests/test_threshold_range_no_cross_dataset_leak.py::test_a_dataset_with_no_values_does_not_inherit_the_previous_range`,
`::test_nothing_is_cached_for_a_column_with_no_values`,
`::test_reset_threshold_range_uses_the_declared_defaults`. Watched failing on
`598ebb01` (with the third case excluded — it names the new symbol): *"the
sliders kept the previous dataset's intensity range: 120.0 – 48000.0"*.

**Probe:** a real `recalculate_threshold` call on a dataset with no values,
after a plate whose range was 120–48000. Before: the range stays 120–48000.
After: 0.0–1.0, the declared default.
