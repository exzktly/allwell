# W4 — the ten items the earlier packages found and could not fix

The "Owed work found while doing this work" section of `../REVIEW_REMEDIATION.md`
holds ten numbered items that three earlier work packages uncovered while doing
something else. Item 4 (the ARCHITECTURE.md deltas) belongs to the lead and is
not touched here; the other nine are this package's list.

Two of them — items 5 and 6 — are the same defect class the whole review is
about: a shortfall that is now correctly *detected* and still cannot be *seen*.
They were done first.

## How the fixes were proved

`scripts/prove_guard.sh` compares against a base ref, and this branch's
checkpoint commits carried earlier work into that history, so a worktree of the
base contains the fix and reports "passed on the base" — a comparison that
measured nothing (CLAUDE.md §7.3 #1). The proof used instead is the one §7.7 #2
prescribes: **revert one line of the fix in place at `HEAD`, run only the tests
that pin it, and require a genuine `AssertionError` about behaviour** — not an
`ImportError` or `AttributeError` on a symbol the fix introduces, which is the
false proof §7.4 #4 warns about.

The scripts are `/tmp/.../w4/mutate.py` and `mutate2.py`, plus the same edit made
by hand for the later items. Each reverts one fix at a time, runs only the tests
that pin it, restores the file, and prints the failure *type* and message. Every
mutation went red with a real `AssertionError`, and the unmutated tree runs each
file green first, so a red mutation is the fix being removed rather than the
harness failing to start.


## Item 1 — `save_to_pipeline_info` was still an unlocked read-modify-write

- **Status:** done
- **Fix:** `well_viewer/domain/sample_definitions.py:138-190` — the read,
  the v1→v2 backup decision and the block replacement now happen inside a
  `_mutate` closure handed to
  `well_viewer.persistence._io.update_json_atomic`, the same guard the other
  two `pipeline_info.json` writers were converted to under item 85. The backup
  is taken *inside* the mutate, so the "was the old block v1?" test is made
  against the bytes actually being replaced rather than a copy read earlier; a
  `backed_up` flag keeps it to one backup per call even when a concurrent write
  makes the mutation run twice, which is what `update_json_atomic`'s docstring
  asks of a mutate with side effects.

  (`well_viewer/persistence/_io.py:73`, `:158`) so this caller keeps the
  `durable=False` it deliberately had. It is the debounced autosave that runs
  on the GUI thread every time the user stops typing a well label, and an
  fsync per pause on a network share is a visible stall; the replace is atomic
  either way, so no reader ever sees a half-written file. Existing callers keep
  `durable=True` by default.

  `update_json_atomic` reports refusals as `False`; both callers of this
  function (the Save button's dialog and the autosave's `logger.exception`)
  key off `OSError`, so the boolean is turned back into one rather than
  becoming a silent no-op autosave.
- **Test:** `tests/test_pipeline_info_concurrent_update.py` —

## Item 9 — `composite_column_rgb` has no ratio or overlay handling

- **Status:** done — **deleted**, not fixed.
- **What was decided and why.** The function is unreachable from the app. The
  Image Table's Separate↔Overlay switch stopped compositing whole columns and
  went to per-cell blending in commit `a35cf9ac` ("Fix Image Table Overlay to
  blend channels into one cell"), which added `overlay_cell_rgb` beside it;
  since then `composite_column_rgb` has had exactly two references in the tree —
  a `# noqa: F401` re-export in `image_table/controller.py` and one test that
  called it directly. `git log -S` finds no live call site at any point after
  that commit.

  Fixing it would mean writing ratio and overlay branches for a function nothing
  can run, and then documenting behaviour the app does not have — the trap
  CLAUDE.md §7.7 #5 names, where the prose raises confidence rather than testing
  it. The two gaps are real *as gaps*: a ratio cell's `chan` is a ratio display
  label and an overlay cell's is the `⊕ OVERLAY` sentinel, and `_load_array`
  resolves neither, so a revived column compositor would silently drop those
  cells from the composite. Leaving dead code carrying that latent behaviour is
  worse than removing it, because the next person to reach for it inherits the
  bug without the finding.
- **Fix:** removed from
  `well_viewer/features/image_browser/image_table/image_compose.py` (the
  function, 1,562 characters) and from the re-export list in
  `image_table/controller.py:78`. `composite_additive_rgb`, which it called,
  stays — `overlay_cell_rgb` and `tests/test_image_table_composite.py` use it.
- **Test:** item 60's behavioural test
  (`test_composite_column_loads_each_cell_with_its_own_render_mode`) had nothing
  left to drive, so the **rule** it pinned is now guarded across the callers
  that can actually run:
  `tests/test_image_table_channel_identity.py::test_every_render_mode_lookup_names_the_channel_it_is_for`
  — an AST check that every `_row_display_opts` call in the `image_table`
  package names a channel. That is eleven live call sites across three modules,
  where the deleted test covered one dead one.
- **Watched fail without the fix:** yes (mutation — `_row_display_opts(ctx, r,
  chan)` at `controller.py:494` reduced to `_row_display_opts(ctx, r)`):
  `E  assert not ['controller.py:493']`.
